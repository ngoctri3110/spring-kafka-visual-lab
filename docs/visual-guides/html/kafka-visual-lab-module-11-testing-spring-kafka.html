Idempotent service không cần Kafka

@Test
void duplicateEventCreatesOneEffect() {
    InMemoryProcessedEvents processed = new InMemoryProcessedEvents();
    InMemoryShipments shipments = new InMemoryShipments();
    ProjectionService service = new ProjectionService(processed, shipments);

    service.apply(event);
    service.apply(event);

    assertThat(shipments.size()).isEqualTo(1);

Lab B · Spring Kafka Test

Chứng minh serializer → broker → consumer

Thêm test dependency

<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-kafka-test</artifactId>
  <scope>test</scope>
</dependency>

Ở Spring Kafka hiện tại, embedded broker dùng KRaft; không thiết kế test mới quanh ZooKeeper.

Boot application với broker test

@SpringBootTest
@DirtiesContext
@EmbeddedKafka(
    partitions = 3,
    topics = "orders.in.it",
    bootstrapServersProperty = "spring.kafka.bootstrap-servers"
)
class OrderListenerEmbeddedIT {
    @Autowired KafkaTemplate<String, OrderPlaced> template;
    @Autowired ShipmentRepository shipments;
}

Arrange → Act → Observe

@Test
void createsShipmentFromKafkaRecord() {
    OrderPlaced event = fixture("evt-101", "order-42");

    template.send("orders.in.it", "order-42", event).join();

    // TODO: poll có timeout hữu hạn cho tới khi shipment tồn tại
    assertThat(shipments.findByOrderId("order-42")).isPresent();
}

join() chỉ đợi producer result. Assertion cuối vẫn phải đợi listener bất đồng bộ bằng polling/latch có deadline—không dùng Thread.sleep(5000).

Nếu assert Kafka record, kiểm tra contract

ConsumerRecord<String, OrderPlaced> record =
    KafkaTestUtils.getSingleRecord(testConsumer, "orders.out.it");

assertThat(record.key()).isEqualTo("order-42");
assertThat(record.value().eventId()).isEqualTo("evt-101");
// TODO: assert topic, header, payload và partition invariant

Topic/group riêng

Spring Kafka khuyến nghị dùng topic khác nhau cho từng test khi có thể. Tạo tên bằng test class/method hoặc UUID; group cũng phải phản ánh mục đích test.

Đừng trộn global embedded broker và broker riêng từng class trong cùng suite. Chúng chia sẻ system properties và có thể gây hành vi khó đoán.

Khi nào chọn Testcontainers?

Khi cần Kafka distribution/image thật, listeners/networking, config broker/client, hoặc cùng lúc khởi động PostgreSQL + Kafka để kiểm tra outbox/idempotent flow.

Đừng biến mọi unit test thành container test

Container startup và Docker tăng chi phí. Giữ suite nhỏ, reuse hợp lý và chạy một nhóm smoke integration test trong CI.

Version note: image tag trong ví dụ là tag từ tài liệu Testcontainers; project thật cần pin tag tương thích và chủ động nâng cấp, không copy “latest”.
Lab D · Failure injection

Chủ động phá đúng một thứ mỗi test

Listener fail N lần rồi success

AtomicInteger calls = new AtomicInteger();
doAnswer(invocation -> {
    if (calls.incrementAndGet() <= 2) throw new TransientException();
    return null;
}).when(handler).apply(any());

// TODO: assert calls=3, effect=1, DLT=0

Luôn fail → DLT

Gửi một record có event ID cố định; chờ record ở DLT với timeout. Assert số attempts theo policy, business effect = 0 và diagnostic context còn đủ.

Duplicate delivery

Gửi hai records cùng event ID. Assert consumer nhận hai deliveries nhưng processed_event = 1 và business effect = 1.

Poison payload

Gửi bytes không deserialize được. Kiểm tra error handler/deserialization strategy đưa record đến recovery path; đừng chỉ assert listener không được gọi.

Broker unavailable

Test producer timeout/fail-fast và readiness behavior ở nhóm container/infra test. Đặt timeout ngắn riêng cho test; không để suite treo theo production timeout.

Rebalance/parallel consumer

Khởi động thêm consumer cùng group, gửi keys khác nhau và assert per-key ordering cùng exactly-one group delivery—không assert thread name hay member assignment cố định.

Active recall

Trả lời trước khi mở

1. Mock KafkaTemplate chứng minh được gì?
Chứng minh code gọi mock với argument mong đợi; không chứng minh serializer, broker ack, topic, partition hay listener.
2. Khi nào pure Java test là đủ?
Khi claim thuộc logic sở hữu trực tiếp: mapping, event identity, key selection, dedup decision hoặc business rule.
3. Embedded Kafka thêm bằng chứng gì?
Producer/consumer thật qua broker test: serialization, topics, keys, headers, listener, offsets và retry wiring.
4. Testcontainers khác embedded broker ở đâu?
Nó khởi động Kafka image thật trong Docker, hữu ích cho distribution/config/network gần production hơn nhưng chậm và nặng hơn.
5. Vì sao producer trước, consumer sau với latest có thể timeout?
Group mới không có offset; latest bắt đầu ở cuối log hiện tại nên bỏ qua record đã tồn tại trước lúc consumer bắt đầu.
6. Vì sao không dùng Thread.sleep?
Sleep vừa chậm vừa flaky: quá ngắn thì fail giả, quá dài thì lãng phí. Poll/latch với deadline dừng ngay khi condition đạt.
7. Test retry thành công cần assert gì?
Số attempts đúng, business effect đúng một lần, event ID giữ nguyên và DLT không có record.
8. Test DLT cần assert gì ngoài việc có record?
Không có business effect, attempts đã hết, payload/key/event identity và diagnostic context đủ để điều tra/replay.
9. Vì sao topic/group dùng chung gây flaky?
Records/history rò giữa tests; cùng group còn phân phối mỗi record cho một member nên test có thể lấy mất input của nhau.
10. Quy tắc chọn tầng test?
Dùng tầng thấp nhất đủ quan sát claim; thêm tầng cao hơn cho các rủi ro framework, broker, infrastructure và journey thực.
