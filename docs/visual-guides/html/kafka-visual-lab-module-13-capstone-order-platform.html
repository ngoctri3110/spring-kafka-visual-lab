Phase B · Transactional outbox

Order commit luôn mang theo publish intent

Một transaction local

@Transactional
public UUID place(PlaceOrder command, String idempotencyKey) {
    // TODO: find existing order by idempotency key
    UUID orderId = UUID.randomUUID();
    UUID eventId = UUID.randomUUID();

    orders.save(Order.pending(orderId, idempotencyKey, command));
    outbox.save(OutboxEvent.orderPlaced(eventId, orderId, command));

    return orderId;
}

Event key và identity

aggregateid=orderId trở thành Kafka key để giữ order per aggregate. id=eventId phải giữ nguyên qua mọi relay attempt.

Chọn relay

# Debezium Outbox Event Router
transforms=outbox
transforms.outbox.type=io.debezium.transforms.outbox.EventRouter
transforms.outbox.route.by.field=aggregatetype
transforms.outbox.route.topic.replacement=outbox.event.${routedByValue}

Nếu dùng poller: claim/lease rows, publish bằng stored event ID, mark sau broker ack và chấp nhận duplicate sau crash.

Phase C · Inventory service

Duplicate delivery tạo một reservation

Unique dedup key

create table processed_event (
  consumer_name varchar(120) not null,
  event_id uuid not null,
  processed_at timestamptz not null default now(),
  primary key (consumer_name, event_id)
);

create table inventory_reservation (
  order_id uuid primary key,
  sku varchar(120) not null,
  quantity integer not null
);

Marker + effect cùng transaction

@Transactional
public void reserve(OrderPlaced event) {
    int inserted = processedEvents.tryInsert(
        "inventory-v1", event.eventId());
    if (inserted == 0) return;

    inventory.reserve(event.sku(), event.quantity());
    reservations.save(new Reservation(event.orderId(), event.sku()));
    // TODO: ghi InventoryReserved/Rejected vào outbox của inventory
}

Business rejection không phải retryable

Hết hàng tạo InventoryRejected; network/DB timeout có thể retry. Deserialization/schema lỗi đi recovery/DLT theo policy riêng.

Phase D · Recovery

Retry có ngân sách, DLT có owner

Transient

Backoff hữu hạn, đo attempts và event age.

Fatal/data

Không retry vô ích; giữ raw/context để chẩn đoán.

DLT

Owner, alert, retention, fix/replay và idempotency.

Policy skeleton

@Bean
CommonErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);
    var handler = new DefaultErrorHandler(
        recoverer, new ExponentialBackOffWithMaxRetries(3));
    // TODO: classify fatal exceptions + RetryListener metrics
    return handler;
}

Replay contract

Replay giữ nguyên event ID. Trước replay phải biết bug đã sửa, consumer idempotent, target topic/group, batch rate và rollback plan.

SLO + alert

Ví dụ: 99% orders đạt CONFIRMED/REJECTED trong 60 giây. Alert theo measured freshness; dùng lag, retries, DLT và broker health để chẩn đoán.

Runbook

Impact → affected group/topic/partition → deploy/traffic/downstream/broker correlation → safe mitigation → prove drain → post-incident action.

Kịch bản trình bày 12 phút

0–2 phút · Kiến trúc và invariants

Chỉ vào transaction boundaries, event identity, Kafka key và ownership.

2–4 phút · Happy path

POST order → order/outbox rows → Kafka record → reservation → result; chỉ rõ event ID xuyên suốt.

4–7 phút · Hai cú crash

Source rollback và relay duplicate. Chứng minh no partial source state và one destination effect.

7–9 phút · Retry/DLT

Transient recover; poison event đi DLT; giải thích replay owner/policy.

9–11 phút · Tests + dashboard

Chạy test matrix quan trọng, mở freshness/lag/listener/broker panels.

11–12 phút · Trade-offs

Nêu giới hạn, version pins, security/PII, scaling bottleneck và bước production tiếp theo.
