Mental model

Đổi “hai commits” thành “một commit + một relay có thể lặp”

Source atomicity

orders và outbox_event dùng cùng datasource/DB transaction.

Eventual delivery

CDC hoặc poller lấy outbox row và publish sau commit.

Destination atomicity

processed_event và projection/business update commit cùng nhau.

Hai transaction cục bộ, không phải một distributed transaction: source DB giữ order+outbox; destination DB giữ dedup+effect.

Mô phỏng 5

CDC hay polling publisher?

CDC / transaction log

  • Gần realtime, không query table liên tục.
  • Insert-only outbox phù hợp Outbox Event Router.
  • Cần Kafka Connect/Debezium và vận hành connector/WAL.

Application poller

  • Dễ bắt đầu trong Spring Boot.
  • Cần claim/lease, batching và SKIP LOCKED khi scale.
  • Crash sau send trước mark tạo duplicate.
CDC / DebeziumPolling
TriggerĐọc database transaction log/WAL.Query rows theo lịch.
Outbox mutationInsert-centric; SMT kỳ vọng INSERT.Thường có READY/IN_PROGRESS/PUBLISHED hoặc lease.
Latency/loadThấp, ít query workload.Phụ thuộc poll interval/batch/index.
Failure concernConnector offsets, WAL retention, schema/config.Claim races, stuck lease, duplicate publish, cleanup.

Lab B · Spring Boot source service

Lưu Order + Outbox bằng một @Transactional

Tạo schema PostgreSQL

create table orders (
  id uuid primary key,
  status varchar(40) not null,
  total numeric(19,2) not null
);

create table outbox_event (
  id uuid primary key,
  aggregatetype varchar(255) not null,
  aggregateid varchar(255) not null,
  type varchar(255) not null,
  payload jsonb not null,
  created_at timestamptz not null default now()
);

create index outbox_event_created_idx on outbox_event(created_at);

Không gọi KafkaTemplate trong request transaction

@Transactional
public UUID placeOrder(PlaceOrder command) {
    UUID orderId = UUID.randomUUID();
    UUID eventId = UUID.randomUUID();

    orderRepository.save(Order.pending(orderId, command.total()));
    String payload = serializeOrThrow(
        new OrderPlaced(eventId, orderId, command.total()));
    outboxRepository.save(new OutboxEventEntity(
        eventId, "order", orderId.toString(), "OrderPlaced", payload));

    // TODO: return orderId; không kafkaTemplate.send(...)
}

serializeOrThrow nên wrap lỗi thành RuntimeException hoặc cấu hình rollback rule. Spring mặc định rollback RuntimeException/Error, không mặc định rollback checked exception.

Test rollback ở khe giữa

Inject failure sau orderRepository.save nhưng trước outbox save. Sau rollback: order rows = 0, outbox rows = 0.

Test commit

Sau success: đúng một order và một outbox row có cùng aggregate ID; event ID không đổi qua mọi relay attempt.

Source invariant: không được có order committed mà thiếu outbox intent. Kafka có thể chậm, nhưng event còn durable trong DB/WAL để relay tiếp tục.
Lab C · Relay và destination consumer

Publish at-least-once, apply effect effectively-once

Debezium Outbox Event Router

transforms=outbox
transforms.outbox.type=io.debezium.transforms.outbox.EventRouter
transforms.outbox.route.by.field=aggregatetype
transforms.outbox.route.topic.replacement=outbox.event.${routedByValue}
transforms.outbox.table.field.event.id=id
transforms.outbox.table.field.event.key=aggregateid
transforms.outbox.table.field.event.payload=payload

Áp dụng SMT có chọn lọc cho outbox table. Mặc định event ID đi vào header id, aggregate ID làm Kafka key.

Nếu dùng poller, claim bằng lease

Đừng giữ lời hứa exactly-once. Crash sau broker ack trước DB mark vẫn tạo duplicate.

Tạo processed_event

create table processed_event (
  consumer_name varchar(120) not null,
  event_id uuid not null,
  processed_at timestamptz not null default now(),
  primary key (consumer_name, event_id)
);

Atomic insert-or-ignore

insert into processed_event(consumer_name, event_id)
values (:consumerName, :eventId)
on conflict (consumer_name, event_id) do nothing;

JDBC update count 1 = lần đầu; 0 = duplicate. Unique constraint xử lý race giữa consumer instances.

External API vẫn cần idempotency riêng

Nếu consumer gọi payment/email HTTP, DB marker không thể rollback remote effect. Dùng idempotency key phía provider hoặc ghi một outbox mới cho bước tiếp theo.

Lab D · End-to-end crash matrix

Phá từng khe và kiểm tra invariant

Source rollback

Throw sau order save trước outbox save. Mong đợi: cả hai bảng 0 rows.

Relay unavailable

Dừng Kafka/connector sau source commit. Order và outbox vẫn tồn tại; khi relay hồi phục event mới xuất hiện.

Relay crash sau broker ack

Poller không mark sent rồi restart. Mong đợi: hai deliveries có cùng event ID.

Consumer không dedup

Trên dữ liệu lab mới, tạm bỏ guard. Hai deliveries tạo hai business effects—ghi bằng chứng rồi khôi phục.

Consumer atomic dedup

Bật PK + transaction. Hai deliveries tạo một processed row và một business row.

Crash giữa marker và effect

Throw sau tryInsert trước business write. Transaction rollback cả hai; redelivery sau đó áp dụng thành công đúng một lần.

Ordering per aggregate

Gửi OrderPlaced rồi OrderCancelled cho cùng aggregate ID. Xác nhận Kafka key giống nhau và consumer quan sát đúng order per partition.

Cleanup/runbook

Định nghĩa retention/cleanup outbox và processed_event, lag/age alert, replay ownership, schema migration và PII policy.

Source evidence

order/outbox counts, same aggregateId, eventId, DB commit.

Relay evidence

connector/poller offset, publish attempts, Kafka metadata, outbox age.

Destination evidence

delivery count, processed marker count, business row/version.

Active recall

Trả lời trước khi mở

1. Vì sao DB-first rồi Kafka không an toàn?
Crash sau DB commit trước Kafka send để lại business row nhưng không có event.
2. Kafka-first rồi DB có giải quyết không?
Không. Crash sau Kafka publish trước DB commit tạo event cho aggregate không tồn tại/không commit.
3. Outbox đảm bảo điều gì?
Khi business row commit thì event intent cũng commit trong cùng DB transaction; relay có thể publish sau.
4. Outbox có đảm bảo Kafka chỉ nhận một record không?
Không. Relay crash sau publish trước checkpoint/mark có thể publish lại cùng event ID.
5. Vì sao event ID phải ổn định?
Consumer cần nhận ra hai deliveries là cùng logical event; relay retry không được tạo UUID mới.
6. Dedup marker vì sao phải cùng transaction với effect?
Tách commit tạo hai lỗi: marker có nhưng effect mất, hoặc effect có nhưng marker mất và redelivery nhân đôi effect.
7. Vì sao PK tốt hơn exists-then-insert?
Unique constraint giải quyết race atomically giữa concurrent consumers; exists check riêng lẻ có thể cùng trả false.
8. Debezium dùng aggregateid làm gì?
Mặc định làm Kafka message key, quan trọng để giữ đúng thứ tự events theo aggregate trong partition.
9. CDC outbox table có nên update trạng thái từng row không?
Outbox Event Router kỳ vọng INSERT operations; UPDATE được xem là invalid theo cấu hình behavior. Cleanup thường dùng retention/delete riêng.
10. Consumer gọi payment API thì DB dedup đủ chưa?
Chưa. Remote effect nằm ngoài DB transaction; cần provider idempotency key, saga/compensation hoặc một outbox cho bước tiếp.
