Kafka Transactions: Exactly-Once nằm trong ranh giới nào?

Transaction có thể commit hoặc abort Kafka output records và consumer offsets cùng nhau. Điều đó rất mạnh cho consume–transform–produce, nhưng không biến database, HTTP hay payment thành một phần của Kafka transaction.

Câu hỏi xuyên suốt: operation nào được transaction coordinator của Kafka commit/abort cùng nhau, và operation nào cần pattern khác?
Mental model

Một bong bóng nguyên tử: output + offsets

Begin

Transactional producer mở transaction có transactional.id.

Stage

Output records và offset kế tiếp được thêm vào cùng transaction.

Resolve

Commit làm cả hai có hiệu lực; abort làm cả hai không có hiệu lực.

Idempotence ≠ transaction: idempotent producer chống duplicate do producer retry trong phạm vi hỗ trợ; transaction còn gộp nhiều writes và consumer offsets thành một đơn vị commit.
Mô phỏng 1

Crash ở giữa nhưng Kafka outcome vẫn là một khối

Input offset 42 tạo output rồi muốn commit offset 43. Chọn kết quả transaction và xem hai state thay đổi cùng nhau.

Dự đoán trước

Output và offset sẽ cùng commit hay cùng abort? DB có rollback theo không?

Crash không kéo DB vào Kafka transaction: nếu DB đã commit độc lập, Kafka abort không đảo ngược row đó. Module 10 sẽ xử lý bằng outbox/idempotent consumer.
Mô phỏng 2

read_committed nhìn qua bộ lọc transaction

Log vật lý vẫn có aborted records và transaction đang mở. Consumer isolation quyết định cái gì được trả về.

Last Stable Offset: với read_committed, record nằm sau transaction đang mở có thể tạm thời bị giữ lại, dù bản thân nó không transactional. Vì vậy consumer có thể chưa đọc tới high watermark.
Mô phỏng 3

Operation này có nằm trong Kafka transaction không?

Nhấn từng operation. “Có Java code trong cùng method” không đồng nghĩa “cùng transaction coordinator”.

OperationTrong Kafka transaction?Điều kiện / thay thế
Records tới nhiều topic/partition cùng clusterCóCùng transactional producer/transaction.
Offsets của consume–transform–produceCósendOffsetsToTransaction(...) và commit transaction.

Mô phỏng 4

Xếp đúng thứ tự Transactional Producer API

initTransactions() gọi một lần sau khi tạo producer; mỗi unit of work đi từ begin đến commit/abort.

beginTransaction()per unit

Lab A · Kafka Java client

Tự viết consume–transform–produce transaction

Lab này dùng Kafka client trực tiếp để thấy rõ framework đang làm hộ điều gì.

Cấu hình consumer chỉ đọc committed output

consumerProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, false);
consumerProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");
consumerProps.put(ConsumerConfig.GROUP_ID_CONFIG, "orders-eos-java-v1");

Cấu hình transactional producer

producerProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG,
                  "orders-eos-java-instance-1");
// transactional.id implies enable.idempotence

try (var producer = new KafkaProducer<String, String>(producerProps)) {
    producer.initTransactions(); // đúng một lần cho producer này
    // TODO: poll loop
}

Mỗi instance đang chạy phải có transactional id riêng để tránh fencing lẫn nhau.

Gộp output và offsets

var records = consumer.poll(Duration.ofSeconds(1));
if (!records.isEmpty()) {
    producer.beginTransaction();
    try {
        for (var record : records) {
            String output = transform(record.value());
            producer.send(new ProducerRecord<>(
                "orders.eos.out", record.key(), output));
        }

        producer.sendOffsetsToTransaction(
            records.nextOffsets(), consumer.groupMetadata());
        producer.commitTransaction();
    }
    catch (KafkaException failure) {
        producer.abortTransaction();
        // TODO: rewind consumer position về committed offsets
    }
}

Rewind sau abort trong raw client

for (TopicPartition partition : records.partitions()) {
    OffsetAndMetadata committed = consumer.committed(partition);
    if (committed != null) {
        consumer.seek(partition, committed.offset());

Abort không tự đưa in-memory consumer position quay lại; Spring listener container xử lý reposition/AfterRollbackProcessor cho bạn.

Không tự resend sau lỗi fatal/fencing

ProducerFencedException cho biết instance khác chiếm cùng transactional.id/epoch. Đóng producer và sửa identity/lifecycle; đừng lặp vô hạn.

Lab B · Spring Boot

Để listener container quản lý transaction

Bật transaction bằng một prefix duy nhất mỗi instance

spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      transaction-id-prefix: "orders-${INSTANCE_ID:local}-"
    consumer:
      group-id: orders-eos-spring-v1
      enable-auto-commit: false
      properties:
        isolation.level: read_committed

Spring Boot tự cấu hình KafkaTransactionManager và gắn vào default listener factory khi property này tồn tại.

Viết listener read–transform–write

@KafkaListener(topics = "orders.eos.in")
void transform(ConsumerRecord<String, OrderCreated> input) {
    OrderValidated output = validate(input.value());
    kafkaTemplate.send("orders.eos.out", input.key(), output);

    if (crashSwitch.failAfterSend(input.value().eventId())) {
        throw new IllegalStateException("lab: abort after send");
    }
}

Container bắt đầu transaction trước listener. KafkaTemplate cùng producer factory tham gia; listener return thì offsets được gửi vào transaction rồi commit.

Không manual ack trong happy-path EOS lab

Với transactional container, offsets được gửi vào transaction theo record/batch listener semantics. Tập trung vào việc method return hoặc throw.

Consumer output phải dùng read_committed

@KafkaListener(
    topics = "orders.eos.out",
    groupId = "orders-output-read-committed-v1",
    properties = "isolation.level=read_committed")
void observeCommitted(OrderValidated output) {
    // TODO: count theo eventId
}

Phân biệt local producer transaction

kafkaTemplate.executeInTransaction(ops -> {
    ops.send("topic-a", "A");
    ops.send("topic-b", "B");
    return null;
});

Nó gộp các Kafka sends trong callback, nhưng không tự gắn offsets của một consumer tùy ý. Consume–transform–produce nên để container transaction làm đúng lifecycle.

Repeated failure dùng after-rollback path

Transactional listener throw sẽ rollback. Dùng DefaultAfterRollbackProcessor để backoff/recover record lặp lỗi; non-blocking @RetryableTopic không kết hợp với container transactions.

Điểm nhớ: listener có thể chạy nhiều lần do rollback. Điều “exactly once” là committed Kafka result đối với read_committed, không phải số lần Java method được gọi.
Lab C · Chạm ranh giới DB

Chứng minh database không rollback cùng Kafka

Chỉ chạy trên database/topic lab. Mục tiêu là quan sát crash window, không phải mẫu production.

Tạo bảng audit lab

create table eos_boundary_audit (
  event_id varchar(100) primary key,
  note varchar(200) not null
);

Commit DB trong transaction riêng

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void commitAudit(String eventId) {
    auditRepository.insert(eventId, "DB committed before Kafka outcome");
}

Gây Kafka abort sau DB commit

@KafkaListener(topics = "orders.eos.boundary.in")
void demonstrate(OrderCreated event) {
    auditService.commitAudit(event.eventId());
    kafkaTemplate.send("orders.eos.boundary.out", event.eventId(), event);
    throw new IllegalStateException("abort Kafka only");
}

Quan sát ba state

DB có một row; output read_committed không thấy record; input group offset không tiến và record được giao lại.

Đừng “sửa” bằng commit-order confidence

Spring có thể synchronize DB/Kafka transaction theo thứ tự, nhưng nếu transaction thứ hai commit fail sau transaction thứ nhất đã commit thì cần remedial/compensation. Đây không phải XA atomicity.

Bước kế tiếp: Module 10 dùng transactional outbox khi cần commit business row và ý định publish event trong cùng một DB transaction.
Lab D · Phá có kiểm soát

Thu bằng chứng cho commit, abort và isolation

Tạo hai topic 3 partitions

orders.eos.in và orders.eos.out; chạy consumer output read_committed và một consumer lab read_uncommitted.

Happy path

Gửi evt-eos-ok. Bằng chứng: output committed nhìn thấy; input group offset tiến từ 42 lên 43.

Fail sau KafkaTemplate.send

Gửi evt-eos-abort, bật crash switch. Listener throw sau send.

So sánh hai output consumers

read_uncommitted có thể nhìn thấy aborted output; read_committed không thấy. Record aborted vẫn chiếm vị trí trong log vật lý.

Kiểm tra input group

Committed offset không tiến; container reposition và giao lại input theo rollback policy.

Tắt crash switch

Lần xử lý lại commit thành công. Consumer read_committed thấy đúng committed result.

Thử fencing trong môi trường lab

Chạy hai instances với cùng transaction-id-prefix. Quan sát fencing rồi sửa để mỗi instance có prefix riêng.

Active recall

Trả lời trước khi mở

1. Kafka transaction gộp hai thứ nào trong consume–transform–produce?
Output Kafka records và consumer offsets kế tiếp được gửi vào cùng transaction.
2. Listener throw sau khi KafkaTemplate.send thì sao?
Container rollback Kafka transaction; output bị aborted và offsets không commit. Input được reposition để đọc lại theo rollback processor.
3. Listener Java có chạy đúng một lần không?
Không nhất thiết. Read/process là at-least-once; committed Kafka result của read–process–write mới đạt EOS cho consumer read_committed.
4. Vì sao output consumer cần read_committed?
read_uncommitted trả cả transactional records đã abort, làm lộ “ghost output”.
5. Database update có nằm trong Kafka transaction không?
Không. Có thể synchronize transaction managers theo thứ tự nhưng vẫn có failure window giữa hai commit; cần compensation/outbox/idempotency tùy bài toán.
6. transactional.id có tác dụng gì?
Nó bật transactional delivery, ngầm bật idempotence và cho phép recovery/fencing giữa producer sessions. Mỗi running instance cần identity/prefix riêng.
7. Abort raw Java producer có tự rewind consumer position không?
Không. Ứng dụng raw client phải seek/reposition; Spring container xử lý phần này.
8. executeInTransaction có tự đưa consumer offsets vào không?
Không cho một consumer tùy ý. Nó tạo local Kafka transaction cho các template operations trong callback; consume–transform–produce container transaction mới tự gắn offsets.
9. Non-blocking retry topic có kết hợp container transaction không?
Không. Spring Kafka nêu rõ hai cơ chế không kết hợp; transactional rollback dùng after-rollback path.
